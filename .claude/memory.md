PATCH when the payload IS the new truth landing in one row of one list — a cell value, a rename, an amendment count; costs no request so the hot path stays as cheap as a local edit. INVALIDATE when the change is STRUCTURAL — a row appearing/moving/disappearing, a column added — because those touch ordering, server-computed counts (subRecordCount, amendmentCount) and derived values (mirrors), and a hand-written patch would have to reproduce the server's arithmetic to stay right. Invalidating a tag nothing is subscribed to is FREE (RTK refetches only what is mounted), which is what lets that file be generous with tags without making the app chatty. Every cell event also invalidates the bare {type:"RecordValue", id:"LIST"} — the tag only getModuleReferences provides — for the same reason updateRecordValue does: mirrors are resolved server-side from other people's cells. GOTCHA HIT AND FIXED: RecordValue.column comes back POPULATED from GET /record-values/:recordId but is a bare id in the document the event carries, so a blind {...existing, ...incoming} silently downgraded an object in the cache to a string; readers tolerate both (`v.column?._id || v.column`) which is exactly why it would have gone unnoticed until something reached for column.type. The merge now keeps the richer one. resyncAfterReconnect() invalidates every tag type on EVERY connect (not just the first): a reconnected client gets a NEW server-side socket, has missed everything in the gap and holds no rooms, and no replay exists — so the honest recovery is to treat what is on screen as stale once. That is the self-healing half: patches make it feel instant, this makes a missed patch survivable. app/providers/realtime.provider.tsx sits INSIDE StoreProvider (it dispatches) and ABOVE the routes, so navigation never drops the connection; it deliberately does NOT disconnect on unmount (React's dev double-mount would kill the socket a moment after opening it). It also joins the ACTIVE workspace room once for the whole app, so the sidebar/Home/members surfaces need no per-page wiring. store/useRealtimeRoom.ts joins per-page rooms and RE-SENDS them on every `connect` — a page that subscribed only at mount would go quiet after the first blip, which looks exactly like the staleness this layer exists to remove. Wired on: the board ({workspaceId, moduleId}), /workspace/[id], its activity + automation pages, and /members/[workspaceId]. TWO POLLS DELETED: store/usePresence.ts no longer beats every 60s (it is now just the status picker — connecting IS the heartbeat, and lib/presence.ts HEARTBEAT_INTERVAL_MS was removed with it), and store/useAutomationRuns.ts dropped pollingInterval/skipPollingIfUnfocused entirely — activity rows are pushed from inside logActivity, so the same cache entry refills on a push instead of a 10s timer; its announce-once/prime logic is UNCHANGED and still needed, because an invalidated refetch returns the same rows repeatedly exactly as a poll did. VERIFIED end-to-end against the live API with two different accounts on one board: cell edit, amendment and record update all reached the other account, the writer got no echo of its own cell, and events carried the ids the patches need. Lint 61 -> 59 pre-existing errors (the removed heartbeat effect cleared two); build clean.
CONEXUS MEET, client (2026-08-27 -- see backend memory for the API, the rooms and the probe): sidebar entry sits directly under Extensions (both are app-level, TbMessages icon, present in BOTH the expanded list and the collapsed rail), route app/Meet/page.tsx. The SHELL is the automation page's, deliberately -- shell card, sticky navbar, BackButton (this page renders no sidebar, so the header is the only way out), workspace icon in the shared NavTile. Inside it is a two-pane layout: components/meet/ConversationList.tsx (left) + ChatPane.tsx (right), plus NewChatModal.tsx, ManageTeamModal.tsx, CallOverlay.tsx. store/api/meet.api.ts adds tagTypes Conversation + Message. ONE LIST, not People and Teams as separate sections -- what orders a chat sidebar is recency, and split sections mean the thread you want is in whichever half you are not looking at. getMessages uses serializeQueryArgs keyed on conversationId ALONE plus merge(), so an older page lands in the SAME cache entry as the first rather than creating a second the UI would have to stitch. sendMessage has NO optimistic patch and NO invalidation: the server echoes the message back to the sender (the one emit with no originId), and the socket bridge appends it -- patching here as well would draw the bubble twice. MESSAGES ARE PATCHED, never refetched: the payload is the whole truth and refetching a transcript to append one bubble would re-download the conversation every time someone typed. TYPING IS NEVER CACHED -- it is re-broadcast from store/realtime.ts as a window CustomEvent (crm:typing) and read by whichever ChatPane is mounted, because caching something worthless a second later means writing and expiring redux state on every keystroke of every participant. CALLS: lib/webrtc.ts CallSession, P2P MESH over the existing socket, free STUN, NO TURN -- roughly one connection in ten (symmetric NAT / strict corporate firewalls) will ring, negotiate and never produce audio, and fixing that needs a paid relay because TURN carries the media by definition. Mesh is honest to ~5 people (each browser uploads N-1 copies of its own stream); bigger needs an SFU. THE SESSION OWNS ITS OWN SIGNALLING (CallSession.attach subscribes to meet:signal filtered by conversationId). It was originally routed by the page through a ref kept in sync during render -- that broke three React rules AND hid a real bug: between setSession() and the effect re-subscribing, inbound ICE candidates went to a closure that still believed there was no call and were dropped, and those late candidates are exactly the ones that make a connection work across the internet rather than only on a LAN. ICE candidates arriving before the remote description are BUFFERED per peer (addIceCandidate throws otherwise). GLARE: the LOWER user id makes the offer, the other sends "ready" and waits -- without an arbitrary-but-shared rule, simultaneous calls leave two half-negotiated connections. end() stops every track or the camera light stays on after the call. The incoming-call prompt is NOT the full overlay: before you accept there is no media and nothing to render, and asking for the camera before someone has agreed to answer is exactly the permission prompt people learn to refuse; the OFFER is carried inside the `incoming` state object (an offer is sent once, so a callee that discarded it would wait for a second that never comes). BUG FOUND AND FIXED by the probe: the page marked a thread read even with the tab BACKGROUNDED, so a message could arrive, clear the badge, and leave the person returning to a conversation that looked read and was not -- an unread count that lies is worse than none because it is trusted. markRead now requires document.visibilityState === "visible" and re-checks on visibilitychange, which is also what makes returning to the tab mark it read. NO RESET EFFECT in ChatPane: the page keys it on the conversation id so switching thread REMOUNTS it and every useState initialiser re-seeds. KNOWN TRADE-OFF, not a bug: with nothing selected the page auto-opens conversations[0], so a new message elsewhere re-sorts the list and can move the view; once the user clicks anything, activeId pins it. Presence dots reuse components/ui/helpers/presenceDot.tsx and the server-derived `presence` field -- never the raw picked status.
